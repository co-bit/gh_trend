# GitHub AI/MCPトレンド観測ダッシュボード 設計書

- 日付: 2026-07-27
- ステータス: 承認済み

## 背景・目的

GitHub公式のtrendingページ(https://github.com/trending)は依存せず、AI関連スキル・MCP(Model Context Protocol)に関するリポジトリの「トレンド」を独自の定義で観測する。結果は1日1回更新されるHTMLダッシュボードとして公開する。

## トレンドの定義

以下3つのシグナルの組み合わせで「トレンド」を定義する。単一の官能的な人気度(スター総数など)ではなく、**変化量**に着目する。

1. **スター増加速度**: 直近7日間のスター数の増加数を1日あたりの増加率に換算し、7日分に正規化した値(`(増加数 / 経過日数) × 7`)。履歴が7日に満たない新規リポジトリでも、履歴が7日分揃った成熟リポジトリと公平に比較できるようにするため、単純な絶対増加数ではなく正規化した値を用いる
2. **話題性(外部言及)**: Hacker Newsでの直近7日間の言及件数(リポジトリの完全一致によるフレーズ検索。曖昧一致による無関係な記事の誤検出を避けるため)
3. **依存関係からの採用度**: GitHubの `/network/dependents` ページに表示される依存リポジトリ数の直近7日間の増加数を、スター増加速度と同様に1日あたりの増加率に換算し7日分に正規化した値

対象スコープは **MCP(Model Context Protocol)と、特定ベンダーに限らない「AIエージェント向けスキル/ツール」全般に絞る**。「スキル」はClaude Skillsに限定せず、OpenAI GPTs、LangChain tools、AutoGPTプラグインなど、エージェントに追加機能を与えるパッケージ全般を対象とする。GitHub Search APIでの新規発見時のキーワード/トピック例:
- MCP: `topic:mcp-server`, `topic:model-context-protocol`
- 汎用スキル/ツール: `topic:agent-skills`, `topic:llm-tools`, `topic:ai-agent-toolkit`, `topic:claude-skill`, `topic:claude-code`

ユーザーの関心に直結するもののみに絞り、汎用的すぎる `topic:ai`, `topic:llm` のような広範キーワードは含めない(ノイズが増えすぎるため)。

## アーキテクチャ

```
GitHub Actions (daily cron, JST 9:00)
  │
  ├─ 1. discover.py  ─ GitHub Search API で MCP/AIエージェントスキル関連の新規リポジトリを発見
  │                     → data/watchlist.json に追加(既存分は保持、上限なし)
  │
  ├─ 2. collect.py   ─ watchlist の全リポジトリについて当日分のシグナルを収集
  │                     ・スター数: GitHub GraphQL API でエイリアスを使い50件ずつ一括取得
  │                       (1リポジトリ1リクエストのREST APIだと数千件規模でActionsの
  │                       レート制限に達し、実行時間の悪化とstar欠損を招くため)
  │                     ・話題性: HN Algolia Search API でのリポジトリ名/URL言及件数
  │                     ・採用度: /network/dependents ページをスクレイピングして件数取得
  │                     ・HN言及・dependentsはリポジトリごとにスレッドプールで並列実行
  │                       (I/O待ちが支配的なため)
  │                     → data/repos/<owner>__<repo>.json に1日分スナップショット追記
  │                     → 90日より古いスナップショットは削除(ローテーション)
  │
  ├─ 2.5. git commit (data/watchlist.json・data/repos/ のみ) → git pull --rebase origin main
  │        latest_scores.json・index.htmlは常に再計算される派生ファイルなので、
  │        生データだけを先にコミット・pullし、以降の計算はpull後の最新状態に対して行う
  │        (派生ファイル同士をgitにマージさせない。2026-08-02にこの順序が逆で
  │        実際にコンフリクト・全収集分喪失が発生した教訓による)
  │
  ├─ 3. score.py     ─ 全スナップショットから各シグナルの変化量を算出し、
  │                     当日追跡中の全リポジトリ内でのパーセンタイル順位に変換、
  │                     6:2:2の重み(スター:HN:Dependents)で合成 → data/latest_scores.json
  │
  ├─ 4. describe.py  ─ 上位20件のうち概要が未登録のリポジトリのみを対象に、
  │                     GitHubのdescriptionをGemini APIで日本語1行に要約
  │                     → data/descriptions.json に追記(既存分は再生成しない)
  │                     GEMINI_API_KEY未設定時は何もせず正常終了する
  │
  ├─ 5. render.py    ─ latest_scores.json から docs/index.html を生成
  │                     (総合ランキング1本 + シグナル別ランキング3本を並列表示)
  │                     descriptions.json があれば概要列にマージする
  │
  └─ 6. git commit & push (data/ と docs/ の残りの変更)
         │
         └─ GitHub Pages が docs/ を配信(mainブランチのdocs/フォルダをソースにする)
```

ディレクトリ構成:

```
scripts/
  discover.py
  collect.py
  score.py
  render.py
  common/          # API呼び出し・パース・パーセンタイル計算などの共通ロジック
data/
  watchlist.json
  repos/<owner>__<repo>.json
  latest_scores.json
docs/
  index.html       # GitHub Pagesの配信元
.github/workflows/
  daily.yml
tests/
  test_score.py
  test_collect_parser.py
  test_render.py
  fixtures/        # dependentsページのサンプルHTMLなど
```

各スクリプトは「前段の出力ファイルを読んで次段の出力ファイルを書く」だけの独立したパイプラインステージとし、単体でも手動実行・デバッグ可能にする。

## データ設計

**`data/watchlist.json`**
```json
[{ "owner": "foo", "repo": "bar", "first_seen": "2026-07-27", "source": "search:mcp-server" }]
```

**`data/repos/<owner>__<repo>.json`**(日次スナップショットの配列、90日分まで保持)
```json
[{ "date": "2026-07-27", "stars": 1234, "hn_mentions": 3, "dependents": 56 }]
```
シグナル取得に失敗した項目は `null` を格納し、欠損として扱う(0扱いにしない)。

**`data/latest_scores.json`**
リポジトリごとに、当日の生値・7日変化量・各シグナルのパーセンタイル・合成スコアを保持する。`render.py` はこのファイルのみを読んでHTMLを生成する。

## スコア計算ロジック

**変化量(velocity)**
- スター増加速度: `today.stars - 7days_ago.stars`(7日分の履歴がなければある範囲で計算)
- 話題性: 直近7日間のHN言及件数の合計
- 採用度: 直近7日間のdependents増加数

**パーセンタイル順位への変換(中間順位)**
当日スナップショットが存在する全リポジトリを母集団とし、各シグナルの変化量を `(自分より小さい値の数 + 同値の数 / 2) / 母集団数` で0〜1のパーセンタイルに変換する。

同値(タイ)には、その同値グループが占める順位範囲の**中央値**を与える。単純な「自分より小さい値の数 / 母集団数」を使うと、母集団の99%がゼロであるようなスパースなシグナルにおいて、ゼロ(=まったく普通の状態)のリポジトリ全員が「全体最下位」と評価されてしまうため。実測では、HN言及がゼロの5,444件(全体の99.5%)がパーセンタイル0.000を付与され、合成スコアの中央値が0.016まで押し潰されていた。

**合成スコア**
シグナルごとに重み付けし、算出できたシグナルの重みで正規化する:
```
composite = Σ(pctl_i × weight_i) / Σ(weight_i)   ※ i は算出できたシグナルのみ
```
欠損シグナルは分子・分母の双方から除外し、0点扱いにはしない。重みは `scoring.py` 冒頭の定数として切り出す:
```python
WEIGHTS = {"star": 0.6, "hn": 0.2, "dependents": 0.2}
```

スター増加を主シグナルとし、HN言及とDependents増加は補助的な重みにしている。後者2つは母集団の99%がゼロで情報量が乏しく、均等重み(各1/3)では「HN言及を1件でも獲得したか」という稀な抽選結果が、スター増加の全レンジ(最下位→1位)と同等の重みを持ってしまい、順位を支配していたため。この2シグナル自体は稀少で有意な情報なので、合成から除外はせずシグナル別ランキングと表示列としても残す。

## HTML出力

`docs/index.html` に以下を表示する:
- マストヘッド(タイトル・並べ替え方針の説明・追跡リポジトリ数・更新日時)
- 総合トレンドスコアによるランキング(1本)
- シグナル別ランキング(スター急上昇 / HN話題 / Dependents急増)の3セクション
- 各リポジトリ行: リポジトリ名・リンク・日本語概要・各シグナルの生値と変化量・成長率・合成スコア
- 各ランキングは上位20件のみ表示する(データ自体は全件収集・保持する)
- 日本語概要は `data/descriptions.json`(describe.pyが生成)からマージし、未登録のリポジトリは「-」を表示する

**4表構成を維持する理由**: シグナル別3表は、総合ランキングに出てこないリポジトリを実測で38件見せている(4表80スロットに対しユニーク58件)。特にDependents急増表は代替不能で、`PrefectHQ/fastmcp`(依存元が週+150、スター成長率は0.6%)のような「静かに採用が広がっているライブラリ」はスター増加では捕捉できない。列の並べ替え機能は表示中20件の再ソートであって母集団からの再抽出ではないため、表を統合する代替にはならない。

**デザインシステム**: CSSカスタムプロパティでライト/ダーク(`prefers-color-scheme`)両対応。寒色のニュートラル(計器系)を基調とし、データを担う3色は色覚多様性検証済みの青・橙・翠を用いる。フォントは丸ゴシック(Google Fonts「M PLUS Rounded 1c」、和文欧文とも対応、システムフォントへのフォールバック付き)を全体に使い、役割の区別はウェイト・サイズ・字間で行う。

**シグネチャ要素: 合成スコアの内訳バー**: 総合ランキング表のスコア列は、3シグナルの寄与を積み上げた横バーで描画する。バーの全長が合成スコア、各セグメントの幅が `重み × パーセンタイル / 算出できたシグナルの重み合計` に対応し、合計は合成スコアに一致する。順位の根拠(スターの勢いで上がったのか、稀少シグナルのボーナスで上がったのか)を開示するのが目的で、公式trendingを信用せず独自定義で計測するという本プロジェクトの趣旨を体現する要素として置いている。内訳バーは総合ランキング表のみに描画し、他3表は数値のみとする(過剰な装飾を避けるため)。

**列の並べ替え**: 各表の列名はボタンで、クリックすると表示中の20件をその列で昇順/降順に並べ替える。`aria-sort`属性で現在の並び順を伝え、キーボード操作にも対応する。並べ替え用の生値は各セルの `data-v` 属性に持たせ、表示文字列のパースに依存しない。欠損値は昇順・降順のどちらでも常に末尾に送る。

静的HTML1ファイルとして生成する。並べ替えのみバニラJavaScript(インラインscript、依存ライブラリなし)を用いる。外部リソースへの依存はGoogle Fontsの読み込みのみ。

## エラーハンドリング

「1リポジトリの失敗で全体を止めない」ことを最優先とする。

- **GitHub REST/Search API**: レート制限時は指数バックオフで最大3回リトライ。失敗が続く場合は該当シグナルを欠損(null)として記録し処理継続。403/429応答・リクエスト例外はいずれも`logging`で警告出力する(以前は無言でリトライしており、レート制限が実際に発生しているか実行ログから確認できなかった)
- **`/network/dependents` スクレイピング**: 非公式HTML構造に依存する最も壊れやすい箇所。パース失敗は例外を握りつぶして欠損値として記録しログに残す。前日値へのフォールバックはしない(欠損はパーセンタイル計算側で対応済み)。APIではなく通常のWebページのため、collect.pyの30並列と同じ同時実行数でアクセスすると429が多発する(実測: 5,518件中4,191件)。このリクエストだけは`MAX_CONCURRENT_REQUESTS = 8`のセマフォで同時接続数を絞り、429時は`Retry-After`ヘッダーを見て必要な時間だけ待機する(GitHub REST/Search APIと同じ`rate_limit_wait_seconds`を共用)。**404**(削除・非公開化・移動済みでリトライしても復活しない)は即座に諦め`RepoGoneError`を送出し、collect.pyがそのリポジトリを`watchlist.json`から除外する。**502**等の一時的なサーバーエラーは429と同じ一般ルートで指数バックオフ再試行する(実測3/5,518件と低頻度で、専用対応は行わない)
- **HN Algolia API**: 同様にリトライ→失敗時は欠損
- **discover.py**: 検索0件・APIエラー時もwatchlist.jsonは前日の状態を維持して処理継続
- **初回実行**: watchlist.json / repos/ が空のケースを正常系として扱う。履歴不足の指標は欠損扱い(0扱いにしない)
- **不正なwatchlistエントリ**: `owner`/`repo`キーを欠いたエントリが混入していても、そのエントリだけを無視して処理継続する(`storage.iter_valid_entries`)。手編集やデータ破損で1件でも壊れると、フィルタが無ければ全リポジトリの収集・スコア計算が丸ごと落ちるため
- **ワークフロー全体**: いずれかのスクリプトが想定外の例外で落ちた場合はその日のcommitをスキップしてActionsを失敗させる(中途半端な状態でcommitしない)

## テスト方針

外部API・スクレイピングに依存する部分はモック/fixture化し、ロジック部分を自動テスト対象にする。

- **`score.py`**: パーセンタイル計算・合成ロジックを純粋関数として切り出しpytestでユニットテスト。欠損混在・母集団1件・全員同値などの境界条件を重点的にカバー
- **`collect.py`のパーサー**: `/network/dependents` のHTMLパース関数を独立させ、保存済みサンプルHTML(fixture)でテスト。実HTTPは叩かない
- **`collect.py`のstar一括取得**: `get_repo_stars_batch`はモックしたGraphQLレスポンスで、複数バッチへの分割・リポジトリ単位の欠損(null)処理・リクエスト失敗時のフォールバックをテストする
- **`daily.yml`**: `git pull --rebase`がscore.py実行より前に来ることを検証する回帰テストを含む(2026-08-02に、この順序が逆だったため派生ファイルのマージコンフリクトでその日の収集分が丸ごと失われた実障害の再発防止)
- **`discover.py`**: レスポンス整形ロジックのみユニットテスト対象。実API呼び出しはテスト対象外(手動dry-runで確認)
- **`render.py`**: サンプルの`latest_scores.json`を入力にHTML生成を確認する簡易テスト
- **E2E**: 日次バッチという性質上、GitHub Actions上での実行自体が実質的な統合テストとなるため重厚なE2Eは組まない。初回は`workflow_dispatch`で手動トリガーして動作確認する

## 実行環境

- GitHub Actions の cron スケジュール(毎日 JST 9:00 = UTC 0:00)
- 実装言語: Python
- GitHub Pages: mainブランチの `docs/` フォルダをソースとして配信
- 認証:
  - GitHub API(Search・REST): Actions標準の `GITHUB_TOKEN` を使用(追加登録不要)
  - Gemini API: `GEMINI_API_KEY` をGitHub Secretsに登録する。日本語概要の自動生成にのみ使用し、未設定でもパイプラインは正常に動作する(概要が「-」表示になるだけ)。当初は「追加のシークレット登録は行わない」方針だったが、日本語概要の自動化にあたり見直した。GitHub純正の無料推論API(GitHub Models)は2026年7月30日に廃止されたため、無料枠とクレジットカード不要という条件を満たすGeminiを採用した

## 既知の制約・将来の検討事項

- `/network/dependents` は非公式ページのスクレイピングであり、GitHub側のHTML構造変更で壊れる可能性がある(エラーハンドリングで欠損扱いにすることで許容)
- 監視対象リポジトリ数に上限を設けないため、長期的にリポジトリ数が増えると1日あたりのAPI呼び出し数・スクレイピング件数が増加する。discover.pyのページネーション追加により監視対象が数千件規模(約5,300件)まで急増したことを受け、HN言及・dependentsの収集はスレッドプールで並列化、star数はGitHub GraphQL APIで50件ずつバッチ取得している。1リポジトリ1リクエストのREST APIのままだと、Actions標準`GITHUB_TOKEN`のレート制限に達し、実行時間の悪化とstar欠損(実測: 全体の約8〜9%)を引き起こすことを実データで確認した。将来さらに規模が拡大しボトルネックになった場合は上位N件への絞り込みを検討する
- `data/repos/`配下は日次でリポジトリごとに1ファイルずつ更新されるため、Gitリポジトリ自体のサイズが時間とともに増加し続ける(90日ローテーションはファイル内の履歴件数を抑えるが、Git履歴自体は減らない)。将来的にリポジトリサイズが問題になった場合は、Git履歴の定期的な圧縮や外部ストレージへの移行を検討する
- 3シグナルの重みはスター:HN:Dependents = 6:2:2([スコア計算ロジック](#スコア計算ロジック)参照)。運用しながら妥当性を見直す余地がある
- GitHub Search APIは1クエリあたり最大1000件(`per_page`×ページネーション)まで取得可能。discover.pyはこの上限までページネーションするが、それでも1つのtopicに数千件のリポジトリが存在する場合は上位1000件までしか発見できない。将来的にボトルネックになった場合は`sort=updated`や作成日フィルタでの絞り込みを検討する
- ページネーション中はGitHub Search APIのレート制限(認証済みで約30リクエスト/分)にかかりうるため、ページ間に短い待機を挟み、403/429応答時は`Retry-After`または`x-ratelimit-reset`ヘッダーを見て必要な時間だけ待機してからリトライする(ヘッダーが無い場合は指数バックオフにフォールバック)
